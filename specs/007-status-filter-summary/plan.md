# Implementation Plan: Status Filter + Summary Row

**Branch**: `007-status-filter-summary` | **Date**: 2026-06-26 | **Spec**: [spec.md](../spec.md)

**Input**: Feature specification from `specs/007-status-filter-summary/spec.md`

## Summary

Add a status filter bar (dynamic pill buttons) above the existing issues table in the web dashboard, plus a summary row below the table showing per-label count and story-point totals for the filtered view. This is a **frontend-only change** — no new backend endpoints or Jira service methods are needed. The existing `GET /api/sprints/{sprintID}/issues` endpoint already returns every issue with its `status` field; filtering and summary aggregation happen entirely in the browser using vanilla JavaScript.

## Phase 0: Research — COMPLETE

This feature has **zero unresolved unknowns**. Key decisions:

1. **Filtering approach**: Client-side only. The existing `getSprintIssues` handler returns all issues with `status` on every issue object. No new API endpoint is needed. Filtering is done by JavaScript array `.filter()` on the already-fetched issue list.

2. **Status pill discovery**: Dynamically derived from the `issues[].status` values of the currently loaded sprint. No hardcoded status list — the filter bar adapts to whatever statuses Jira returns for each team.

3. **Summary computation**: Client-side aggregation using existing `issues[]` data. For each configured label, count issues whose `activeLabels` include that label and sum their `storyPoints`. This mirrors the logic in `labelreport.Aggregate()` but runs in JavaScript.

4. **No backend changes**: `internal/dashboard/handler.go` and all Go structs (`DashboardIssue`, `SprintIssuesResponse`) remain unchanged. The `DashboardIssue.Status` field is already present in the existing response.

## Phase 1: Design & Contracts

### Frontend State Extension

Extend the existing `state` object in `app.js` with one additional property:

```javascript
const state = {
  selectedTeam: null,
  selectedSprint: null,
  selectedStatuses: new Set(),   // NEW: status values selected by user; empty = show all
};
```

### Status Filter Bar Rendering

After `renderTable(data)` is called (within `fetchIssues`), insert a status filter bar above the table:

```
<div id="status-filter-bar">
  <span>Status:</span>
  <button class="pill" data-status="To Do">To Do</button>
  <button class="pill" data-status="In Progress">In Progress</button>
  <button class="pill" data-status="In Review.">In Review.</button>
  <button class="pill" data-status="Closed">Closed</button>
</div>
```

- Unique statuses are extracted from `data.issues[].status`.
- Buttons are sorted alphabetically.
- All buttons start in "deselected" state (no `.active` class).

### Status Pill Toggle Logic

When a pill is clicked:
- Toggle the `data-status` value in `state.selectedStatuses`.
- If the set is now empty, show all issues (clear filter).
- If non-empty, re-filter the issues list to only those whose `status` is in the set.
- Re-render the table body rows (hide/show, not full re-render).
- Re-render the summary row.

### Summary Row Rendering

Append a `<tfoot>` row to the existing table:

```html
<tfoot>
  <tr class="summary-row">
    <td colspan="4">Summary</td>
    <td>Label: count / SP</td>
    <td>Label: count / SP</td>
    <td>...</td>
  </tr>
</tfoot>
```

For each configured label:
- Count = number of filtered issues whose `activeLabels` include that label.
- Total SP = sum of `storyPoints` for those issues (0 if no story points).

### Data Model

No backend data model changes. The existing `DashboardIssue` struct already has `Status string` and `ActiveLabels []string`. The frontend introduces:

- **StatusFilterState** (frontend only): A `Set<string>` of status values selected by the user. Empty set = no filter.
- **FilteredIssueSet** (frontend only): Result of `issues.filter(issue => state.selectedStatuses.size === 0 || state.selectedStatuses.has(issue.status))`.
- **SummaryTotals** (frontend only): Per-label `{ count: number, totalSP: number }` computed from `FilteredIssueSet`.

### Error Handling

- No new error paths introduced. The existing error banner (`showError`) is reused if a status pill somehow references an unknown status (edge case: malformed Jira response).
- Empty sprint (zero issues): existing "No issues found" message is shown; status filter bar and summary row are not rendered (consistent with current behavior).
